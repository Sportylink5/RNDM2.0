RNDM Chat v53 — Краткий отчёт проверки и честные ограничения

ПРОВЕРЕНО/РЕАЛИЗОВАНО
1. Авторизация и Supabase: серверные RPC проверки ролей Owner/Admin/Moderator, функции без авторизации не открывают приватные данные.
2. Ник/имя/название/описание: серверные BEFORE-триггеры. Лимиты 15/15/50 символов.
3. IP-регистрация: PostgreSQL Before User Created Auth Hook. Соль хранится в закрытой схеме rndm_private, в реестре только SHA-256 отпечаток IP. Обязательна ручная активация хука.
4. Аномалии: 6 одинаковых сообщений / 2 минуты, 5 каналов / час, 2-3 регистрации по одному IP -> события для персонала.
5. Owner: доступ к до 50 сообщениям за запрос при наличии подробной причины, запись в admin_audit. Другим ролям недоступно.
6. Точная регистрация: auth.users.created_at; серверная проверка ролей и логирование чтения.
7. Удаление: Edge Function owner-security-actions с JWT и повторной проверкой роли, запретом удаления Owner/Admin и самого себя, вводом username и причины, журналом действия.
8. Доступность: существующие аккаунты и сообщения оставлены, старые длинные поля не обрезаны.
9. Frontend: согласованность ES-модулей, расширенная защита ввода, мобильная адаптация.
10. Privacy: явное уведомление о доступе Owner в рамках расследования.

ОСТАТОЧНЫЕ РИСКИ И ОГРАНИЧЕНИЯ
- Система НЕ предоставляет end-to-end encryption: сообщения технически доступны серверу и владельцу в рамках модерации.
- IP лимит не учитывает старых аккаунтов и не обходит VPN/смену IP; может затрагивать невиновных пользователей за общим IP.
- Часть вложений личных чатов всё ещё находится в публичном Supabase Storage bucket chat-files (из v52). Требуется миграция в PRIVATE bucket и раздача signed URL, иначе обладатель прямой ссылки может открыть файл.
- Некоторые SECURITY DEFINER функции для авторизованных ролей всё ещё требуют отдельного ручного аудита.
- Для защиты от DDoS открытого Supabase API необходим инфраструктурный WAF/Proxy. robots.txt не блокирует злонамеренных ботов.
- Auth Hook необходимо включить в Authentication → Hooks.
- Удаление Auth может быть заблокировано наличием объектов Storage; в этом случае функция возвращает ошибку без утверждения об успехе.
- Сквозного автоматизированного E2E-прогона с двумя действительными аккаунтами нет. Отправка сигналов, реальная блокировка IP в Auth после включения и hard-delete данных не проверялись в production.
- Текст privacy.html — технический образец, не юридическое заключение.
